Introduction
With reference to the Object Oriented Programming model, objects that are distributed across different address spaces and are capable to work together by sharing data and invoking methods, are termed as Distributed Objects.
Address spaces may be on same computer with multiple processes, or on multiple computers within a network.
Also, objects are the communicating entities, which hide the underlying complexity of distributed programming.
Providing Location Transparency, distributed objects generally communicate with RMI (Remote Method Invocation).

Remote Procedure  Call (RPC)
An interaction between a client and server, where the client invokes a procedure remotely residing on a server.
Server executes the procedure and pass the result back to the client; in the mid time of the call, calling of the procedure is blocked or halted, which is resumed only after getting result from server.
Based on the single-process procedure call model, it is a high level network communication interface.
A server process consists of a service interface which defines the procedures available for remote calling, works under request reply protocol omitting the object reference from request messages.

----- slide 8 -----
The client procedure calls the client stub in the normal way.
The client stub builds a message including parameters, name or number of procedure to be called, and calls the local operating system. The packaging of arguments into a network message is called marshalling.
The client sends the message to the remote OS via a system call to  the local kernel. To transfer the message some protocol (either connectionless or connection-oriented) are used.
The remote OS gives the message to the server stub.
The server stub unpacks the parameters and calls the server.
The server does the work and returns the result to the stub.
The server stub packs it in a message and calls its local OS.
The server's OS sends the message to the client's OS.
The client's OS gives the message to the client stub.
 The stub unpacks the result and returns to the waiting client procedure.

Benefits
Despite being local, called Procedure can be executed in different process and machines.

----- slide 10 -----
RPC Issues
Due to the distant location of a particular caller and provider of procedure call, sometimes the normal functioning might be disrupted due to following reasons:
The client is unable to locate the server
The request message from the client to the server is lost (Lost request message)
The reply message from the server to the client is lost (Lost Reply Message)
The server crashes after receiving a request (Server Crash)
The client crashes after sending a request (Client Crash)
In RPC, under some above fault conditions, Call Semantics defines when and how often a remote procedure may be executed.

----- slide 11 -----
Call Semantics
Calling semantics must be same whether procedure is implemented locally or remotely.
Exactly once: It is hard to achieve in practice, based on use of time-outs, retransmissions, same call identifier and cache associated with the callee.
At most once (may-be): It requests RPC only once (no reply may mean that no execution took place) 
At least once: It keeps requesting RPC until valid response arrives at client.
Last once: Based on timeouts, retransmitting of request for procedure call is done until result of procedure execution is received.
Last-of-many call: Neglects orphan calls (whose caller has expired due to node crash) and only accepts the call when identifier associated with it matches to most recent call.

Remote Method Invocation (RMI)
A communication mechanism among the distributed objects, where methods invocation between objects in different processes takes places, either on same machine or separated.
Each process consists of a set of objects. These objects may receive local invocation or remote invocation or both.
Objects receiving remote invocation are called Remote Objects.

----- slide 19 -----
Design Issues in RMI
Shares same design issues as discussed in RPC in terms of programming with interfaces; call semantics and level of transparency
Mainly, 2 issues are important to deal in  making remote invocations
Number of times the methods are invoked in response to single remote invocation
Level of location transparency 
Semantics
Exactly once invocation semantics – Every method is executed exactly once. (Ideal situation)
Maybe invocation semantics - The invoker can not determine whether or not the remote method has been executed.
Types of failures:
Omission failures if the invocation or result message is lost.
Crash failures when the server containing the remote object fails. 
Useful for applications where occasional failed invocation are acceptable.

----- slide 20 -----
At-least-once invocation semantics:
The invoker either receives a result (in which case the user knows the method was executed at least once) or an exception.
Types of failures:
Retransmitting request masks omission failures.
Crash failures when the server containing the remote object fails.
Arbitrary failure when the remote method is invoked more than once, wrong values are stored or returned.  An idempotent operation that can be performed repeatedly with the same effect can be a solution.
Useful if the objects in a server can be designed to have idempotent operations.

----- slide 21 -----
At-most-once invocation semantics:
The invoker either receives a result (and the user knows the the method was executed exactly at most once) or an exception.
All fault tolerance methods executed.
Omission failures can be eliminated by retransmitting  request.
Arbitrary failures can be prevented by ensuring that no method is executed more than once
JAVA RMI and CORBA use at-most-once semantics. CORBA also use maybe semantics for methods that do not return results. SUNRPC provides at-least-once semantics.

----- slide 22 -----
Providing reliable request-reply protocol
Fault-tolerant Measures 
Retry request message: whether to retransmit the request message until either a reply is received or the server is assumed to have failed.
Duplicate filtering: when retransmissions are used, whether to filter out duplicate requests at the server.
Retransmission of results: whether to keep a history of result messages to enable lost results to be retransmitted without re-executing the operations at the server

Java RMI case study
Java RMI extends the Java object model to provide support for distributed objects in the Java language.
It allows objects to invoke methods on remote objects using the same syntax as for local invocations.
Type checking applies equally to remote invocations as to local ones.
Programming distributed applications in Java RMI is simple.
It is a single-language system.
The programmer of a remote object must consider its behavior in a concurrent environment.

----- slide 45 -----
[in the slide picture] The client thread's socket specifies a local IO port to be used for sending messages (or
the IO port can be chosen by the operating system).
The client's socket also specifies the address of the destination machine and the port
number that is expected to be bound to the server thread's socket.
The server's socket specifies a local IO port for receiving messages. Messages can be
received from any client that knows both the server's machine address and the port
number bound to the server's socket.
The client issues a request to the server to form a connection between the two sockets.
Once the server accepts the connection request, messages can be passed in either
direction across the channel.
